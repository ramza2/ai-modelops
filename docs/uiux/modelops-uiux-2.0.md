# ModelOps UI/UX 2.0 — 운영 관제형 인터페이스 설계 기준
작성일: 2026-11-18 · 추적: [Issue #102](https://github.com/ramza2/ai-modelops/issues/102)

## 1. 목표 / 우선순위
Netdata의 **상태와 지표를 한눈에 읽는 정보 밀도**, Dozzle의 **간결한 탐색·문제 확인 흐름**을 참고한다. 서비스 운영자가 "현재 상태 → 문제가 있는 대상 → 확인할 화면"을 1~2번의 이동으로 파악하게 한다. **디자인 재구성이지 백엔드 운영 기능 재설계가 아니다.**

우선순위는 (1) 운영 안전 (2) 사실성·신뢰 (3) 문제 인지 속도 (4) 접근성·반응형 (5) 미관이다.

## 2. 명시적 비범위
- 첫 단계에는 새 Backend/Gateway/Worker/Node Agent API, DB 마이그레이션, Docker runtime, GPU/모델 교체, 추론 설정 변경을 넣지 않는다.
- 15초 자동 갱신 주기, 조회 엔드포인트, 기존 오류 격리 및 이전 성공 데이터 유지 계약 변경 금지.
- 서버에서 수집하지 않는 시계열 데이터를 임의로 생성하거나, 분산된 배포별 P95를 합쳐 전역 P95인 것처럼 표시하지 않는다.
- 정확하지 않은 '실시간' 표현 금지: 실제로는 15초 주기의 폴링 기반 관측이다.
- 위험한 관리 동작(Stop/Restart/Purge/Switch)을 대시보드에 원클릭으로 추가하지 않는다.
- 차트 패키지, 상태관리 프레임워크 등 신규 의존성은 UX20-A에서 추가하지 않는다.

## 3. 정보 구조 (화면 순서)
1. **운영 요약/주요 지표**: Management Health/Ready, 서버 ONLINE/전체, 모델 HEALTHY/RUNNING, API Serving/Enabled, 최근 24시간 호출 성공률·오류 건수, 진행 중인 작업. 비교 분모·기간 명시.
2. **확인이 필요한 항목**: 실제 API 오류, 비정상 집계(집계 가능한 경우에만), 최근 실패 Operation. 모든 항목은 해당 조회 화면 링크 제공. 실패 조건 확인되지 않으면 '정상 확인'이라고 단정하지 않는다.
3. **서버·모델·API 연결 요약**: 각 상세 페이지(/nodes, /deployments, /endpoints)로 이동할 수 있는 간결한 상태 영역.
4. **최근 24시간 사용 현황**: 기존 집계값과 배포별 상위 목록. 미수집값 표시와 집계의 한계 유지; /observability로 이동.
5. **최근 작업 목록**: 상태, 작업 유형, 시간, 오류를 스캔하기 쉬운 표; /operations 및 가능한 /operations/:id로 이동.
6. 상세 용어 안내는 보조 접힘 영역에 두어 중요 정보보다 위에서 화면을 차지하지 않게 한다.

## 4. 데이터·상태 표현 계약
- `0`: 성공적으로 조회해 값이 실제 0.
- `미수집`: 정상/부분 응답이지만 지표값 없음.
- `확인 불가`: 해당 섹션 조회 실패.
- `이전 수집값`: 새로고침 실패했지만 이전 성공 응답 표시 중인 경우; 성공 시각 유지.
- 조회 실패가 일부 있어도 성공한 섹션은 계속 표시. 모든 요청 실패 시 별도 전체 오류.
- `deploymentsRunning`과 `deploymentsHealthy`는 다른 조건의 쿼리 결과이며 합/차를 근거 없이 장애 수로 해석하지 않는다. `endpointsServing`과 `endpointsEnabled`도 독립 집계임을 표시한다.
- 24시간 성공률은 기존 `aggregateInvocations`를 그대로 사용. 요청 0건은 '데이터 없음'이지 100% 성공이 아니다.
- 단순 색상만으로 상태를 구분하지 않고 레이블 및 보조 아이콘을 제공.
- 실제 문제 우선: 상세 현황과 연결되는 링크가 없는 경고 카드는 만들지 않는다.

## 5. UX20-A: 대시보드 첫 구현 범위
허용 수정:
- `frontend/src/pages/DashboardPage.tsx`
- `frontend/src/styles/app.css` (새 클래스는 `.dashboard-v2` 범위로 한정)
- `frontend/src/test/DashboardPage.test.tsx` 및 필요한 관련 테스트
- 필요 시 대시보드 전용 하위 컴포넌트 1~2개 (별도 패키지 추가 금지)

구현 방향:
- 카드의 수를 무조건 늘리지 않고 정보 위계를 만든다. 데스크톱은 4열 안팎의 주요 KPI, 태블릿/모바일 자동 래핑.
- 심플한 기업형 스타일: 뉴트럴 배경, 얇은 보더, 충분한 정보 간격, 강조 색 절제. 기존 `--bg`, `--surface`, `--text`, `--muted`, `--accent` 등 토큰을 존중하고 라이트/다크 모드 모두 지원.
- 상단에 핵심 요약을 배치하고, 관리 시스템 Health/Ready 정보를 중복된 숫자 카드와 배지로 따로 보여주지 않는다.
- 조회 가능한 상세로 실제 이동하는 명확한 텍스트 링크 제공.
- 새로고침 버튼, loading/refreshing 상태, abort/unmount, 이전 성공 갱신시각 유지.
- 기존 24h group_by=deployment, 8개 최근 작업, page_size=1 count 조회 및 원본 API 계약 유지.
- 자동으로 UX20-B 공통 Shell까지 확장하지 않는다.

검증:
- 부분 실패/전체 실패/자동 갱신 실패·복구, '0/미수집/확인 불가', 요청 0건, 검색·상태별 링크, 320px 화면, 키보드 접근성.
- `cd frontend && npm test -- --run`, `npm run typecheck`, `npm run build` (기존 저장소 절차에 맞게 실행)
- React/Vitest 회귀 테스트 통과 후 Draft PR. 실제 운영 배포/병합은 별도 검토.

## 6. 후속 단계
- **UX20-B AppShell**: 좌측 메뉴 압축·계층, 현재 위치 및 의미 있는 활성 상태, 반응형 내비게이션, 토큰·컴포넌트 공통화.
- **UX20-C GPU/모델 화면**: Node 자원 조회·vLLM runtime latest/history의 실제 시계열만 시각화. 시간축/단위/결측 구간 표기, 모델/배포/노드 출처 분명히.
- **UX20-D 운영 모니터링**: 로그·Health·운영 이력 연결, 필터/상태별 빠른 탐색 및 근거 링크. 새로운 임의 Docker 제어는 금지.
- **UX20-E 안정화**: 전체 화면 회귀·브라우저 운영 인수검사, 이후 필요할 때만 별도 API 확장 논의.

## 7. 비기능 수용기준
- 기존 `/dashboard`, `/nodes`, `/models`, `/deployments`, `/endpoints`, `/observability`, `/operations`, `/clients` 라우트 유지.
- 표시 문구는 한글 위주, Status/Endpoint 등 전문 용어는 설명과 함께 병기.
- 운영 데이터가 없거나 부분 실패해도 읽기 가능한 대시보드.
- CSS는 기존 화면에 예상치 못한 영향이 없도록 범위 지정.
- 대상 브랜치 PR은 squash merge 방식 권장; Node/GPU/Backend/DB/AI Gateway 컨테이너 재시작 없이 Frontend 단독 배포 가능해야 한다.
